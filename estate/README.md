# estate

A small, generic AWS test bed that Deliberator runs against: service A (inbox queue to DynamoDB, publish to
EventBridge, ack endpoint) and service B (bus event to ack in A and a row in Postgres `acks`), a Node Lambda
logger, one Terraform module for Floci and real AWS. Java 21, Spring Boot 3.3.

- `bb estate:build|deploy|up|status|down [--ws W]`: Maven, `terraform apply` on Floci, services as runtime containers (derived from their descriptions).
- Each service module carries a `deliberator-service.edn` (its description); `bb estate:up` attaches this repository, adopts them (`service.adopt`) and starts them (`service.start`); `dlb service list|stop|start|restart|build`.
- Config chain: `application.properties` placeholders, then `terraform/modules/stack/taskdef.json.tftpl` (ECS `environment` and `secrets`), then SSM `/estate/...` and secrets `estate/api-key`, `estate/db-password`.
- Correlation: `X-Correlation-Id`, SQS attribute `correlation`, `detail.correlation`; on every log line as `[%X{correlation}]`.
- `APP_AUTO_PUBLISH` (default false): service A publishes to the bus as soon as it stores an inbox message; `bb estate:up --auto-publish` turns it on. Off, `POST /publish/{id}` does it.
- JDWP: A on 5005, B on 5006. Rebuild a service with `bb estate:build && bb estate:up`.
- The chain (brief §6): `POST /schedule` on the HTTP API (`api/main` in the local environment, Floci serves it at `<endpoint>/_aws/execute-api/<id>/%24default`) or a direct `lambda invoke function/scheduler-create` creates a one-off EventBridge Scheduler schedule (group `estate-chain`); when it fires, `ecs-scale` sets the desired count of the ECS service `estate-service-a` (deployment controller `CODE_DEPLOY`, M5 deploys to it) and puts the SSM parameter `/estate/chain/desired-count`. `ANY /log` on the same API goes to the `logger` Lambda. `order.scn` runs it end to end (`estate/lambda/{logger,scheduler-create,ecs-scale}`, `terraform/modules/stack/chain.tf`).
- `terraform/iam` is the second root: the role `estate-shared`, which `terraform/aws` looks up by name, so `terraform.graph` finds the order `iam`, `aws` and `dlb terraform apply-all` applies them in it (onto Floci through the override file `terraform.local` writes; the tests apply copies with `prefix=m6a`). `terraform/floci` keeps its own endpoints and is run by `bb estate:deploy`.
- `terraform/aws` with `-var run_services=true` (default off) is the real running estate: ECR repositories (`bb estate:real-images --prefix P --profile PROFILE` builds the two images with Podman and pushes them), a task role, the awslogs driver as the only log path, a security group (8081-8082 from the VPC and from `-var 'allowed_cidrs=["<your address>/32"]'`, 5432 for the `sql` step from the same), a Cloud Map private DNS namespace (B reaches A as `service-a.<prefix>.local`), public IPs in the default VPC's subnets (no NAT gateway, no load balancer), and Postgres as a sidecar container of B's task. Both services start at desired count 0; push the images, then `aws ecs update-service --desired-count 1` for each (about $0.06/h for the two Fargate tasks). The tasks' public IPs change whenever a task is replaced (the chain scales A to 3 and back): put the current ones in the environment's `service/a`, `service/b` and `db/main` targets (a password for `db/main` belongs in a `PGPASSFILE` the daemon sees, not in the record). `scenarios/order.scn` takes every name and wait from the environment's targets (`scheduler/chain`, `parameter/chain-desired`, `ecs/cluster`, `ecs/service-a`, `function/ecs-scale`, `timing/chain`, `timing/logs`), `scenarios/remote-kinds.scn` runs every step kind with an AWS backend (also needs `queue/probe`, `queue/probe-name`, `parameter/probe`).
- `terraform/aws` is applied only to a sandbox AWS account for tests (`-var prefix=m4chain`, optionally `-var with_ecs=true`), then destroyed; it never has the CODE_DEPLOY service (needs an ALB).
- `bb acceptance [--ws W] [--down]` runs `estate/scenarios/order.scn` and `estate/scenarios/payloads/*.scn` against it.
- The deploy pipeline (M5.4): `estate/.github/workflows/deploy.yml` (`workflow_dispatch`): job `build` builds service A's image (`services/service-a/Dockerfile`, Maven in one stage, the JRE in the other, `docker build` through the runner's socket), job `deploy` runs `ci/register-taskdef.sh` (a new task-definition revision of the service with that image) and `ci/deploy.sh` (a CodeDeploy deployment with an AppSpec, polled to the end). `terraform/floci/codedeploy.tf` has the application `estate` and the deployment group `service-a` for the CODE_DEPLOY service. `dlb ci local . estate/.github/workflows/deploy.yml deploy` runs it with `act` on the runtime's Podman against Floci; `dlb deployed refresh|show` then lists the service's PRIMARY task set (`ci_local_estate_test`, tour chapter 14).
